# 自动行程守护真机原型

打开 `TripProbe.xcodeproj`，选中配对的 iPhone，使用你在 Xcode 中配置的开发团队构建 `TripProbe`。最低系统为 iOS 17。测试使用独立的 App「Life Mem 守护测试」，Bundle ID 为 `dev.kolafish.lifemem.tripprobe`，与 Life Mem 正式路线存储隔离。坐标只用于内存中的移动判断。测试记录事件计数、相对延迟和采样时长。

## 开始和停止

1. 在测试 App 点「设置定位权限」，按系统提示允许使用期间定位和精确位置。再次点「设置定位权限」以请求「始终」。如果系统在稍后显示升级提示，可在系统设置确认「始终」。
2. 可选地允许运动辅助。随后点「开启监听」，确认状态为「低功耗监听」。
3. 测试结束后点「停止监听」。在运行期间撤回「始终」也会停止监听。主动划掉 App 的场景单独测试，重新打开后会检查之前的授权和监听设置。

监听使用显著位置变化和 Visits。五分钟内的出发信号可以启动最多 45 秒的移动验证。连续可靠速度，或运动识别与位移相符时，进入高精度采样。连续三分钟无移动证据，或一轮高精度累计达到 15 分钟后，退回低功耗监听。界面显示的事件延迟以系统事件时间为起点。测起步漏段时，在出发前点「标记这次出发」，看到「已标记，可以锁屏出发」后立即锁屏，之后查看首个有效点的相对延迟。标记用于测量延迟，等待系统定位事件触发移动验证。后台唤醒验证单独测量，避免点按动作让 App 保持在前台。

## 真机验收

- 确认「后台 App 刷新」状态，记下「显著位置回调（含初始）」「停留回调（含到达）」和「低功耗监听错误」的累计次数，与出门后读数对照。原始回调包含初始化或到达事件，因此可能增加而没有启动验证。前台开启监听后，时间戳落在启动后 15 秒内的显著位置样本按初始化处理，之后的首次新样本可以进入移动验证。由定位事件唤醒时直接检查样本是否新鲜。
- 锁屏分别走一段短途和较长步行路线，再测骑行和乘车。每种场景记录实际出发次数和「确认移动」的增量，计算漏录率。对识别成功的场景记录从真实出发到第一个有效点的延迟。
- 室内静置以及行程结束后静置，分别记录「启动验证」「确认移动」的变化，核对静止误启动和三分钟降频路径。
- 单独观察系统后台重启、用户主动划掉后重新打开、拒绝和撤销「始终」、拒绝运动权限。模拟器可检查权限前界面，传感器和后台唤醒结论以真机为准。
- 一天保持监听，另一天关闭监听，使用相似路线和屏幕时长，在 iPhone 电池设置比较测试 App 的用量。对照高精度采样时长解释差异。

共享结果时只用计数、相对延迟和用量，省略真实坐标及行程时间。

## 定位对照

在守护监听关闭时进入「定位对照」。点「开始对照」，如有系统提示，允许使用 App 期间的精确位置。蓝点是 MapKit 自带的当前定位，紫圈的中心是应用直接收到并画出的 Core Location 坐标。本次采样持续 45 秒，离开页面或切入后台会提前停止。坐标和读数仅留在页面内存中。

橙圈预览从原始坐标换算到高德坐标的候选结果。蓝点和橙圈都出现时，对照熟悉的道路或建筑。反馈只需说橙圈是否接近蓝点，以及「蓝点与橙圈中心距离」的读数。后台守护测试和正式路线使用各自的数据。

## 静止后恢复对照

停止低功耗监听，点「测试静止后恢复」。本轮启用系统实时定位和后台定位会话，可能增加耗电。等状态为「已静止，等待出发」，下次日常出门时锁屏即可。每次系统报告静止后再次交付移动位置，累计一次恢复。可选的「标记这次出发」用于估算实际出发到恢复的间隔。停止监听后可查看本轮统计，再次开启该测试会开启一轮新统计。第一次启动实时定位不计为移动后恢复。对照时两种模式都应以相同方式标记实际出发，系统离开停留事件的投递延迟属于另一项指标。
